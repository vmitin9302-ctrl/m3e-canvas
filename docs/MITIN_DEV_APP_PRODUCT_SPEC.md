# MITIN DEV — Product Spec

Статус: кликабельный прототип. 06.09.2026. Репозиторий: `vmitin9302-ctrl/m3e-canvas`.

## Для кого и зачем

Клиент малого бизнеса проходит путь от идеи до сопровождения и понимает, что происходит с его проектом. Владелец MITIN DEV работает один: ему нужны факты, договорённости, материалы и следующее действие без дополнительной бюрократии.

Две стороны одного проекта должны использовать существующую CRM и один backend. Приложение не становится второй CRM.

## Две роли

| Роль | Доступ и задачи | Нижняя навигация |
| --- | --- | --- |
| `client` | Свои заявки, проекты, этапы, согласование демо, материалы, стоимость, проектное общение, поддержка | Главная / Проект / Сообщения / Профиль |
| `owner` | Администратор MITIN DEV: заявки, проекты, статусы этапов, решения клиентов, сообщения, аналитика | Главная / Заявки / Проекты / Ещё |

В будущем backend определяет роль после авторизации. В приложении нет переключателя роли. Единственный выбор «Я клиент / Я владелец» находится на отдельном экране `DEMO · роли`. Переключение экранов через панель M3E — инструмент разработчика, а не часть продукта и не механизм безопасности.

## MVP продукта

1. Заявка с типом проекта: сайт, бот, CRM, автоматизация, AI, своя идея.
2. Бриф: бизнес-задача, функции, диапазон бюджета, желаемые сроки, интеграции, комментарии; проверка и редактирование до отправки.
3. Кабинет после согласования проекта: стоимость, факт оплаты, остаток, текущий этап, ожидания и действия.
4. Этапы: ТЗ, дизайн, разработка, проверка, запуск, сопровождение.
5. Демо: открыть, одобрить или оставить правки.
6. Материалы: перечень, состояние комплектности, добавление материалов.
7. Простое проектное обсуждение без обещания интеграции с MAX/VK/Telegram.
8. Поддержка: проблема, доработка, новый проект; отображение активного сопровождения.
9. Сторона владельца: список/карточка заявки, создание связанного проекта, статусы этапов, согласование, входящие, аналитика.

Это целевой функциональный MVP. В этой ветке реализован только прототип интерфейса: ввод и изменения живут в памяти Preview. Ни один реальный сервис MVP не подключён.

## Заявка не равна заключённому проекту

Отправка создаёт только демонстрационную заявку №1045. Бюджет — пожелание клиента, не цена договора. После «Создать проект» владелец видит новый связанный проект в состоянии согласования; цена, оплата и срок не заполнены вымышленными договорённостями.

Переход «Главная клиента · демо» показывает другой подготовленный этап сценария: уже согласованный проект `p001` из заявки №1042. Это прямо объяснено на экране подтверждения. Поддержка помечена как отдельный пример состояния после запуска; она не меняет текущую разработку в Production.

## Budget range

Единое поле — существующий `Lead.budget_range`. Подписи прототипа строго соответствуют заданию:

| Подпись |
| --- |
| до 10 000 ₽ |
| 10–20 тыс. |
| 20–40 тыс. |
| 40–70 тыс. |
| 70 тыс.+ |
| пока не знаю |

Перед интеграцией проверить реальные значения enum/сериализацию существующей CRM. Схема CRM в рамках этой задачи не читалась и не менялась. Новую независимую классификацию не вводить.

## Сценарии

**Клиент:** Welcome → Создать проект → Тип → AI-бриф → Детали → Проверка → Заявка принята → Главная клиента (подготовленный пример после договора) → Проект → Этап → Демо. Ветки: изменить бриф; демо одобрить/правки; добавить материал; сообщения; расходы; поддержка; профиль.

**Владелец:** Dashboard → Заявки → Карточка → Принять / изменить статус → Создать проект → Карточка нового проекта → Этапы. Отдельно: Проекты → действующий проект → этапы → изменение статуса → клиент видит изменение в том же Preview.

**Общие значения в одной сессии:** task, features, project_type, budget_range, deadline, integrations, comments, lead_status, stage_0…stage_5, current_stage, demo_status, demo_feedback, materials_status, client_message, owner_message, support_last.

При закрытии Preview значения сбрасываются. JSON и Android prompt содержат исходные вымышленные значения, а не текст, введённый при тестировании.

## Demo data и аналитика

Источник: `prototypes/mitin-dev/demo-data.json`. Все имена, контакты, проекты и суммы вымышленные; единственный email использует домен `.test`. Реальные РиТМассаж и DIVEEV STUDIO заменены на «Точку баланса» и «Линию». Реальная клиентская информация и готовые сайты не использованы.

В исходной выборке 6 заявок, 3 связаны с проектами, 2 активных проекта, 1 на сопровождении, 2 ожидают клиента, 2 непрочитанных сообщения. Конверсия равна 3 / 6 = 50%. Источники: приложение — 1, Telegram — 1, сайт — 2, рекомендация — 2. Все шесть бюджетных диапазонов отображаются, включая нулевые.

Фильтры и аналитика — **срез demo data на 06.09.2026**, а не live-расчёт изменяемой CRM. Изменение статуса в Preview не перекладывает карточку между списками и не пересчитывает выборку.

## Дизайн

Material 3 Expressive: графитовые поверхности, фиолетовый акцент, rounded shape, system font, emphasized type, expressive motion, стандартные M3 card/list/select/button/navigation компоненты. Телефонные фреймы 412×892 dp. Нет игровых метрик, неоновых диаграмм или выдуманного прогресса в процентах. Финансовые суммы и следующее действие заметнее вторичных метаданных.

Нативный Canvas содержит экранные заметки и заметки о поведении, которые попадают в Android prompt. Русские подписи интерфейса сохраняются; обрамление сгенерированного prompt — английское, потому что русский язык генератора исходный M3E не поддерживает.

## Что не входит в эту ветку

Production API, FastAPI endpoints, PostgreSQL, миграции, реальные credentials/аккаунты/данные, отправка уведомлений, реальный AI, платежи, фактические загрузки файлов, APK/AAB, публикация приложения, merge, deploy, изменения bizflow-business-system и legal/РКН документов.

## Следующие возможности, отдельно от прототипа

После отдельного согласования: авторизация с отзывом сессий, подключение существующего backend, серверная изоляция клиентов, российское объектное хранилище, подтверждённые условия проектов, версия ТЗ/история решений, поиск по своим материалам, уведомления с настройками, интеграция каналов по выбранной модели. AI-бриф требует отдельной модели доступа к данным и проверки владельцем перед договорённостями.
